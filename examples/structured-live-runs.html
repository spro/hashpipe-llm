Captured live runs

Five grounded llm.structured workflows

Each example combines a typed model response with a deterministic post-check. The first two are focused runs; the next two show multi-stage chains over a real project file and current API data; the final one exercises typed containers and unions.

1. Extract commands from the project README

Validation passed

In plain English: give the model the README and ask it to make a trustworthy command list, with a quote from the README proving each entry.

Hashpipe script
files.cat README.md
| llm.structured {
    commands: [{
      name: ["llm", "llm.json", "llm.structured", "llm.models"],
      purpose: "Concise purpose",
      evidence: "Exact supporting excerpt from the supplied README"
    }]
  } "List every documented package command. Copy its command name exactly
     and give a short purpose. For each result, include an exact supporting
     excerpt from the supplied README."

3. README evidence inventory → learning plan

2 stages passed

In plain English: first find out what the package can really do from its README; then use only those verified capabilities to create a three-step learning plan.

Chain script
$inventory = files.cat README.md
| llm.structured {
    capabilities: [{
      command: ["llm", "llm.json", "llm.structured", "llm.models"],
      role: ["freeform_text", "json_parsing", "schema_validated_output", "model_discovery"],
      evidence: "Exact README excerpt supporting this capability"
    }]
  } "Create one capability record for each documented command. Use each role
     exactly once. Include an exact supporting excerpt."

$inventory
| llm.structured {
    lessons: [{
      sequence: "integer: Lesson number from 1 to 3",
      focus: ["prompting", "structured_extraction", "model_selection"],
      primaryCommand: ["llm", "llm.json", "llm.structured", "llm.models"],
      exercise: "One concise hands-on exercise",
      expectedOutput: "Expected result shape"
    }]
  } "Create a three-lesson progression from the supplied capability inventory.
     Use only commands represented in the input. Sequence must be 1, 2, 3."

4. HN API intake → thematic editorial digest

2 stages passed

In plain English: turn a larger batch of live Hacker News posts into a short editor’s briefing: what leads, which ideas connect, and what else deserves attention—without letting the summary invent stories.

Chain script
use http

# Fetch the current top 12 IDs, then request all twelve story objects in parallel.
$hn = "https://hacker-news.firebaseio.com/v0"
$ids = http.get $hn/topstories.json @ 0..12
$source = $ids || http.get $hn/item/$!.json

$intake = $source | llm.structured {
  stories: [{
    id: "integer: Copy the input id exactly",
    title: "Copy the input title exactly",
    score: "integer: Copy the input score exactly",
    category: ["technology", "science", "policy", "business", "culture", "other"],
    rationale: "One short category rationale based only on title"
  }]
} "For each item, copy id, title, and score exactly. Categorize from title only."

# The second model call receives only the validated stage-one records.
$intake @ stories | llm.structured {
  headline: "Single concise digest headline",
  featured: {
    id: "integer: Copy an input id exactly",
    title: "Copy its input title exactly",
    angle: "What makes this the lead"
  },
  themes: [{
    label: "Short theme label",
    storyIds: "integer[]: Input story IDs supporting this theme",
    summary: "One-sentence synthesis based only on those titles"
  }],
  watchlist: [{
    id: "integer: Copy an input id exactly",
    title: "Copy its input title exactly",
    reason: "Why it is worth following"
  }]
} "Create an editorial digest from the supplied stories only. Select exactly one
   featured story, create 2 to 4 themes, and include 3 to 5 different watchlist
   stories. Copy every returned ID and title exactly; use only input IDs in themes."

5. Normalize delivery details with typed containers

Validation passed

In plain English: copy a small delivery record while constraining an array to allowed labels, preserving a two-dimensional list of numbers, keeping a nested address object, and accepting either kind of reference ID.

Hashpipe script
{recipients: ["to", "cc"], measurements: [[12.5, 8], [3, 4.25]], address: {street: "1 Main St", city: "Boston"}, reference: 4921}
| llm.structured {
    recipients: {type: "array", description: "Delivery recipient roles", items: ["to", "cc", "bcc"]},
    measurements: {type: "array", description: "Rows of numeric measurements", items: {type: "array", items: "number"}},
    address: {type: "object", fields: {
      street: "Street address",
      city: "City"
    }},
    reference: {anyOf: ["string", "integer"], description: "Customer or order id"}
  } "Copy the supplied delivery details exactly"
Live structured output
{
  "recipients": ["to", "cc"],
  "measurements": [[12.5, 8], [3, 4.25]],
  "address": {"street": "1 Main St", "city": "Boston"},
  "reference": 4921
}

Post-check: the live result deep-equaled the supplied record: recipient labels stayed within the enum, every measurement remained numeric, the nested address shape was preserved, and the numeric reference satisfied the union.

These are captured outputs from live requests, not fixtures. Structured output enforces shape; deterministic checks enforce provenance and any business rules that the schema cannot express.
